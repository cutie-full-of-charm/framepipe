# Бэкенды декодирования (`HWAccel`)

> ВЕрсия при написании: `0.4.2.dev4`.  
> Реализация декодирования -- FFmpeg `libav*`, доступность конкретного кодека и аппаратного профиля определяется сборкой FFmpeg и драйвером.  
> Основной упор тестирования: VAAPI.  
> D3D11VA практически не тестировался.

`hwaccel` выбирает только место декодирования, не способ конвертации пикселей и не место хранения результата. Полный набор параметров: `hwaccel`, `postprocessor`, `output_memory`, `out_format`.  
Матрица совместимоти: [compatibility.md](compatibility.md).

## `HWAccel.SOFTWARE`

- Платформа: там, где работает используемая сборка FFmpeg.
- Формат декодированного кадра: программный `AVFrame`, формат выбирается декодером (`yuv420p`, `nv12`, другие форматы FFmpeg)
- Постпроцессинг: `PostProcessor.CPU`.
- Выходная память: `MemoryType.CPU`.
- Выходные форматы: `BGR24`/`RGB24`/`GRAY8` через swscale, `NATIVE` без изменения размера.
- Цвет: CPU-конверсия через FFmpeg/libswscale, без явной настройки цветовой матрицы.

Типичный путь: `SOFTWARE → CPU → CPU`. Это конфигурация Python `Reader` по умолчанию (кроме того, что выходной формат по умолчанию в Python — BGR24).

## `HWAccel.VAAPI`

- Платформа: Linux; Win явно запрещает VAAPI-декодирование.
- Hardware pix_fmt: `vaapi`, реальный underlying software format поверхности определяется декодером/драйвером, его нельзя приравнивать к `frame.pix_fmt == "vaapi"` у GPU-поверхности.
- Условие:  сейчас `av_hwdevice_ctx_create` берет фиксированный `/dev/dri/renderD128`, это может не работать в вашей системе.
- Драйвер: при отсутствии переменной `LIBVA_DRIVERS_PATH` программа пытается найти драйверы в директориях: `/usr/lib/x86_64-linux-gnu/dri`, `/usr/lib64/dri`, `/usr/lib/dri`, `/usr/local/lib/dri`
- Постпроцессинг: `CPU`, `VAAPI`, `OPENCL` (последний только при VAAPI NV12 и успешном interop).
- Выходная память: CPU или GPU в зависимости от постпроцессора, `VAAPI + GPU` разрешён только с `NATIVE`.
- Выходные форматы: `BGR24`/`RGB24`/`GRAY8`/`NATIVE` с ограничениями конкретного процессора.

VAAPI наиболее отлаженный бэкенд текущей разработки. Для GPU->GPU можно оставить поверхность в виде `VaapiFrame(surface_id)`, для CPU->numpy доступны скачивание и конвертация, OpenCL позволяет обрабатывать NV12 без промежуточной CPU-конверсии при поддержке межбэкендного отображения памяти.

Код выполняет `vaSyncSurface` перед обработкой, отдельные повреждённые поверхности могут пропускаться без excetion и закрытия сессии, при 25 ошибках декодирования сессия пытается восстановится. Это не означает восстановление при любой ошибке драйвера.

## `HWAccel.CUDA`

- Платформа: наличие CUDA-совместимой конфигурации, драйвера NVIDIA и CUDA runtime.
- Hardware pix_fmt: `cuda`б underlying software format определяется FFmpeg.
- Постпроцессинг: `CPU` (скачивание hardware frame) либо `CUDA` (GPU-конвертация/resize через .cu CUDA kernel).
- Выходная память: для CPU-постпроцессора RAM, для CUDA-постпроцессора RAM или GPU (DLpack).
- Форматы: CPU-путь зависит от возможностей swscale и скачивания, CUDA-постпроцессор явно требует 8-битный NV12 и даёт `BGR24`, `RGB24`, `GRAY8` (но не `NATIVE`).
- Цвет для CUDA-постпроцессора: фиксированные коэффициенты BT.709 limited, без учёта метаданных матрицы и диапазона исходника, в дальнейшем поддержка скорее всего расширится.

CUDA-постпроцессор находится в отдельной динамической библиотеке `_framepipe_cuda.so` (`.pyd` для Windows) и загружается по необходимости. Пример [06_zero_copy_inference](../../examples/06_zero_copy_inference.py) использует GPU-вывод и DLPack для PyTorch.

Наличие `HWAccel.CUDA` не означает, что конкретный поток обязательно декодируется на CUDA: перед запуском проверяется наличие аппаратной конфигурации нужного кодека в FFmpeg, если её нет, инициализация завершается ошибкой. Никакие fallback при неправильных для конкретного оборудования конфигурациях не предусмотрены. Пайплайн просто упадет (в версии `0.4.2.dev4`, он упадет в reboot-loop без явной ошибки конфигурации, это цель №1 для исправления сейчса)

## `HWAccel.D3D11VA` -- очень сыро и экспериментально

- Платформа: ветка `D3D11VA` выбирает D3D11 только на Windows, на Linux выбор отвергается.
- Hardware pix_fmt: определяется конфигурацией FFmpeg, обычно D3D11.
- Постпроцессинг: только `PostProcessor.CPU`
- Память результата: только `MemoryType.CPU`
- Форматы результата: `BGR24`, `RGB24`, `GRAY8`. `NATIVE` только без изменения размера и то с оговорками.
- Маршрут: D3D11 hardware frame -> `av_hwframe_transfer_data()` -> CPU FFmpeg swscale / native.

## Общие ограничения

1. Аппаратное декодирование запрашивается для конкретного FFmpeg-декодера: если `avcodec_get_hw_config` не нашёл нужное устройство, будет ошибка, не программный fallback. В версии `0.4.2.dev4` подобная ошибка неявно уведет reader в бесконечный loop перезапуска, это цель №1 для исправления.
2. Если аппаратный декодер вернул программный кадр вместо ожидаемого hardware pix_fmt, это будет воспринято как ошибка.
3. Выбор `HWAccel` не определяет, какая цветовая матрица будет использована при преобразовании: это зависит от `PostProcessor`, см. [pixel-formats-and-color.md](pixel-formats-and-color.md).
4. Проверенные на одной машине декодер/драйвер/формат нельзя автоматически считать проверенными на другой.

## Пример выбора и диагностики

```python
from framepipe import HWAccel, Reader

with Reader("video.mp4", name="hw-demo", hwaccel=HWAccel.VAAPI) as reader:
    while reader.is_opened():
        frame = reader.read_new_frame()
        if frame is not None:
            print(reader.hwaccel_active, frame.pix_fmt, frame.memory_type)
```

`hwaccel_active` сообщает активное имя устройства FFmpeg после открытия сессии в stdout, проверяйте логи и логи драйвера/FFmpeg вместе с `frame.pix_fmt`, а не только параметр `hwaccel_requested`
Если reader не смог выйти в состояние STREAMING на тестовом файле, с большой вероятностью, конфигурация не поддерживается/некорректна (`0.4.2.dev4`).
