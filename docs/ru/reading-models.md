# Модели чтения и доставки кадров

> Версия при написании: `0.4.2.dev4`  
> Описана фактическая семантика публичной Python-обертки `framepipe.Reader` и реализации `src/reader.cpp` для данной версии, в дальнейшем могут быть изменения API

## Две независимые оси: получение и представление

Нужно различать:

1. Модель доставки: читать текущий слот (`read`), читать его только при обновлении (`read_new`), дождаться обновления (`read_latest`) или запрашивать декодирование следующего кадра (`on_demand` + `next`).
2. Представление результата: получить `numpy.ndarray` (`read*` без `_frame`) либо объект `Frame` (`read*_frame`). Выбор `Frame` не меняет модель доставки.

В обычном режиме (`on_demand=False`) работает producer в отдельном потоке. После декодирования/постпроцессинга он записывает `Frame` в единственный текущий слот, увеличивает `frame.id` и будит ожидающих потребителей. Отдельной очереди опубликованных кадров в интерфейсе нет.

```text
Поток декодирования / producer:    F1 ── F2 ── F3 ── F4 ── F5
                                     │    │    │    │    │
Публикуемый слот:                  [F1] [F2] [F3] [F4] [F5]
                                     ^         ^         ^
Медленный потребитель:             read      read      read
                                     F1        F3        F5

F2 и F4 были декодированы и опубликованы, но потребитель их не забрал
```

Это и есть latest / drop на уровне доставки -- старое значение слота замещается новым. Скорость источника, декодера, постпроцессора, GPU-синхронизация и Python-обработка имеют значение.

## Сводная таблица методов

| Задача | numpy (только packed CPU) | Объект `Frame` | Блокирует? | Пропуски между обращениями? |
| --- | --- | --- | --- | --- |
| Прочитать текущий кадр | `read()` | `read_frame()` | Нет | Да; один и тот же кадр может повториться |
| Прочитать, только если есть новый | `read_new()` | `read_new_frame()` | Нет | Да; повтор того же `id` отсекается |
| Дождаться нового | `read_latest(timeout)` | `read_latest_frame(timeout=1.0)` | Да, максимум `timeout` секунд | Да; возвращает последнюю публикацию, а не очередь |
| Получить следующий кадр по запросу (файл) | `next()` | `next_frame()` | Да, до кадра/EOF/ошибки/stop | Не пропускает *из-за медленного потребителя* |

В любой из трёх первых строк результат может быть `None`, если подходящего кадра нет; для `read_latest*` это также происходит при таймауте, остановке или завершении on-demand. Для `next*` `None` означает EOF/остановку при отсутствии нового кадра. `read_frame()` фактически также может вернуть `None` до первой публикации, хотя аннотация Python-обёртки не отражает этого.

Ограничение numpy API: `read()`, `read_new()`, `read_latest()` требуют `output_memory=MemoryType.CPU` и `out_format` из `BGR24`, `RGB24`, `GRAY8`. Для GPU или `NATIVE` используйте методы `*_frame()`. `next()` в Python-обёртке не делает предварительную проверку формата, но конвертация в NumPy на стороне C++ всё равно требует упакованный CPU-кадр.

### `read()` и `read_frame()` -- снимок текущего слота

Возвращают последний доступный результат немедленно. Не ждут первого кадра и не помечают кадр как "прочитанный" для `read_new*`/`read_latest*`.

```python
from framepipe import Reader

with Reader("video.mp4", name="snapshot", realtime_file=True) as reader:
    frame = reader.read_frame()  # Frame или None; повторные вызовы могут дать тот же id
    if frame is not None:
        print(frame.id, frame.width, frame.height)
```

Подходит для рендеринга в своём цикле, мониторинга и ситуации "покажи то, что есть прямо сейчас". При частом опросе один и тот же кадр может приходить многократно. Здесь нет ожидания новой публикации.

### `read_new()` и `read_new_frame()` — non-blocking latest, без дублей

Возвращают текущий слот, только если `id` отличается от последнего, выданного через `read_new*` или `read_latest*`, иначе -- `None`. Фоновый producer не притормаживает и ничего не складывает в очередь, поэтому быстрые кадры между двумя вызовами будут пропущены потребителем.

```python
from framepipe import Reader

with Reader("video.mp4", name="preview", realtime_file=True) as reader:
    while reader.is_opened():
        frame = reader.read_new()  # ndarray или None; без ожидания
        if frame is None:
            continue
        # Отобразить кадр или передать в обработчик
```

Если loop занят тяжёлой обработкой, это поведение обычно желательно для realtime ML/CV: не накапливается очередь старых кадров. Однако показанный цикл активно опрашивает Reader и может расходовать CPU, пока публикаций нет. В прикладном коде часто предпочтительнее `read_latest*`.

### `read_latest(timeout)` и `read_latest_frame(timeout)` — ждать новый latest

Поведение близко к `read_new*`, но вместо немедленного `None`, когда обновления нет, вызов ждёт новую публикацию или завершение указанного времени. Если новый непрочитанный `id` уже есть, возвращается сразу. `timeout` измеряется в секундах, должен быть неотрицательным. `timeout=0` превращает вызов в проверку без ожидания.

```python
from framepipe import Reader

with Reader("rtsp://camera.example/live", name="detector") as reader:
    while reader.is_opened():
        frame = reader.read_latest_frame(timeout=1.0)
        if frame is None:
            # Таймаут или остановка: это не «пустой видеокадр».
            continue
        # inference(frame): обрабатываем актуальный кадр, не очередь отставших
```

Это ожидание обновления текущего слота, а не API чтения всех кадров, накопленных за время обработки. Между вызовами потребитель всё равно может пропускать опубликованные кадры. `read_latest` (numpy) в Python-обёртке требует явно передать `timeout`; у `read_latest_frame` есть значение по умолчанию `1.0`.

Общий указатель: методы `read_new`, `read_new_frame`, `read_latest`, `read_latest_frame` используют в C++ общий `_last_read_id` конкретного Reader. Если один потребитель уже взял `id=42` через `read_latest_frame()`, то следующий `read_new()` не выдаст снова этот `id`. Это не четыре независимых подписчика. Несколько конкурентных потребителей на одном Reader тоже будут разделять этот указатель, а не получать каждому одинаковую последовательность.

### Пример: режим read-latest-drop для inference loop

```python
from framepipe import Reader

with Reader("rtsp://camera.example/live", name="edge-inference") as reader:
    previous_id = None
    while reader.is_opened():
        frame = reader.read_latest_frame(timeout=0.5)
        if frame is None:
            continue
        if previous_id is not None and frame.id > previous_id + 1:
            print("Пропущено публикаций:", frame.id - previous_id - 1)
        previous_id = frame.id
        # Здесь может быть сравнительно медленная ML/CV обработка кадра.
        # Очередь старых опубликованных кадров не накапливается.
```

Разница между ID -- пропущенные публикации Reader, а не обязательно потери кадров исходного потока: `Frame.id` назначается уже обработанному результату, при публикации. Для измерения end-to-end задержки нужны отдельные замеры с учётом PTS, времени поступления, буферизации источника и скорости обработчика.

## Файлы: `realtime_file=False` и `realtime_file=True`

Оба варианта используют тот же фоновый latest-слот, если `on_demand=False`. Параметр `realtime_file` меняет темп работы producer, а не семантику `read*`.

| Параметр | Режим обработки файла | Что увидит потребитель |
| --- | --- | --- |
| `realtime_file=False` (по умолчанию) | Декодирование без искусственного ожидания PTS, настолько быстро, насколько позволяет pipeline | При медленном чтении может успеть увидеть только последние кадры/один кадр; для полного прохода файла этот режим не подходит |
| `realtime_file=True` | Между кадрами выставляется задержка на основе PTS относительно первого кадра | Ближе к воспроизведению с исходным темпом, но `read*` по-прежнему видит один перезаписываемый слот и может пропускать публикации |

Реализация PTS pacing сейчас наивная: polling `sleep_for(1 ms)`, ориентируется на `monotonic` clock, пропускает ожидание при отсутствии PTS/невалидном time base или если уже опаздывает. Это не точная синхронизация аудио/видео и не гарантия стабильного FPS. Для источников, распознанных как live, ожидание `realtime_file` вообще не применяется.

## `on_demand=True` — последовательный pull для файла

Это отдельный режим producer: рабочий поток запускается, но ждёт запроса от `next_frame()` / `next()`, после которого выдаёт один успешно обработанный кадр. Новый запрос не поступит, пока потребитель сам не вызовет `next*` ещё раз. Вызов блокирует до результата, EOF или ошибки (и может завершиться после `stop()`). Чтение пакетов/декодирование может потребовать больше одного пакета на выходной кадр, а повреждённые VAAPI-кадры могут быть пропущены механизмом восстановления.

```python
from framepipe import Reader

with Reader("video.mp4", name="offline", auto_start=False, on_demand=True) as reader:
    reader.start()  # обязателен, если auto_start=False
    while True:
        frame = reader.next_frame()  # Frame / None (EOF)
        if frame is None:
            break
        # Обрабатываем кадр до запроса следующего
        print(frame.id, frame.pts)
```

- Только для источников, которые Reader классифицирует как FILE. С распознанным live URL конструктор бросит исключение.
- `on_demand=True` несовместим с `realtime_file=True`. Он не нуждается в искусственной паузе PTS: темп определяет потребитель.
- `next_frame()` поддерживает CPU/GPU/NATIVE. `next()` возвращает numpy только для packed CPU-результата.
- При `auto_start=True` (значение по умолчанию) поток запускается конструктором и остаётся ждать первого запроса; `reader.start()` повторно вызывать не нужно.
- На EOF `next*` возвращает `None`. Ошибки внутри on-demand сессии прокидываются в вызывающий код, а не обрабатываются бесконечным переподключением.
- Наличие режима не означает стопроцентную сохранность каждого кадра исходного кодека при ошибках декодирования или повреждении поверхности; его назначение — последовательная доставка результатов без потерь из-за медленного Python-потребителя.

`on_demand` используется в [06_zero_copy_inference](../../examples/06_zero_copy_inference.py): следующая выдача запрашивается после инференса по предыдущему кадру.

> Не подменяйте `next*` на `read_latest*` в режиме `on_demand`: `read_latest*` не создаёт запрос на декодирование, а только ждёт изменения уже опубликованного слота. Для продвижения файла вызывайте `next_frame()` или `next()`.

## Как выбрать модель

| Цель | Выбор | Почему |
| --- | --- | --- |
| Камера / edge inference с приоритетом актуальности | `read_latest_frame(timeout)` | Удобный блокирующий latest-drop; нет очереди старых кадров |
| GUI или периодическая проверка доступного изображения | `read()` / `read_frame()` | Мгновенный снимок последнего состояния |
| Собственный неблокирующий цикл обработки | `read_new()` / `read_new_frame()` | Нет дублей; отсутствие обновления сразу возвращает `None` |
| Видео как поток «в реальном времени» для демонстрации | `realtime_file=True` + `read_new()`/`read_latest()` | Файл воспроизводится примерно по PTS, но это всё ещё latest-drop |
| Офлайн-инференс/конвертация с обработкой кадр за кадром | `on_demand=True` + `next_frame()` | Скорость задаёт потребитель, нет замещения непрочитанных результатов |
| CUDA / OpenCL / VAAPI surfaces, `NATIVE` | Методы с `_frame` | Возвращают типизированное хранилище вместо принудительного NumPy |
