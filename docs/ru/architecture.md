# Архитектура и жизненный цикл кадра

> Версия при написании: `0.4.2.dev4`, интерфейсы и ограничения могут измениться.

## Пайплайн

В общем случае, рабочий пайплайн выглядит так:

```text
файл / RTSP / другой источник, распознаваемый FFmpeg
  │
  V
FFmpeg demux + video decoder -- HWAccel (SOFTWARE / CUDA / VAAPI / D3D11VA)
  │
  V
InputTransfer: RefTransfer, или трансфер hardware VRAM -> CPU RAM
  │
  V
IFrameProcessor: CPU / CUDA / VAAPI / OpenCL
  │                преобразование формата и/или изменение размера
  V
OutputTransfer: без копирования / CUDA->CPU / VAAPI->CPU
  │
  V
Frame: CpuPacked / CpuPlanar / Cuda / Vaapi / OpenCLBuffer / OpenCLImage
  │
  V
Reader: последний кадр / новый кадр / запрос кадра
```

Важные моменты:

1. `hwaccel` -- декодирование. Даже если оно выполняется на GPU, постпроцессор CPU может скачать кадр на хост.
2. `postprocessor` -- обработка. Например, VAAPI->OpenCL работает с VAAPI-декодированием и OpenCL-конвертацией.
3. `output_memory` -- размещение после обработки. RAM, CUDA, VAAPI surface, OpenCL GPU buffer -- разные варианты хранения.
4. `out_format` -- формат результата. `NATIVE` сохраняет нативное представление в рамках пайплайна. Фактический итоговый формат пайплайна можно получить через `frame.pix_fmt`

Матрица допустимых комбинаций: [compatibility.md](compatibility.md).

## Режимы чтения

### latest-drop

Базовый, изначально задуманный и проработанный режим, подразумневает свежесть и отсутствие очереди устаревающих кадров: producer работает в отдельном потоке, не зависит от python-обработчика, и каждый новый кадр перезаписывает предыдущий. В общем, все остальные режимы были как бы приделаны к этому, какие-то более удачно, какие-то менее удачно. Подробности по каждому методу -- в [reading-models.md](reading-models.md).

### Фоновое декодирование

При `auto_start=True` (именно такое значение по умолчанию) создаётся рабочий поток, который непрерывно обрабатывает входные кадры и публикует последний в слоте. Методы `read_frame()` / `read()` читают слот (могут повторять кадр), в то время как `read_new_frame()` / `read_new()` читают слот только при изменении ID, `read_latest_frame(timeout)` ожидает новый кадр до таймаута. Если потребитель медленнее декодера, промежуточные кадры будут пропущены.

### Чтение по запросу (`on_demand=True`)

`reader.next_frame()` инициирует получение одного кадра. Используется для файлов, требует `reader.start()` при `auto_start=False`, несовместим с `realtime_file=True` и с live источниками. Отличается от фонового доступа к "последнему кадру" тем, что так при обработке файлов вы не пропустите ни одного кадра, декодировав их все последовательно, в нужном теспе, см. [06_zero_copy_inference](../../examples/06_zero_copy_inference.md).

### PTS и realtime

`realtime_file=True` пытается выдерживать интервалы между PTS локального файла, текущая реализация использует polling с шагом 1 мс, что может создать проблемы при очень большом fps. Для live источников параметр игнорируется в любом случае, но в метаданных PTS кадра будет (если он нужен вам для, например, подбора наиболее близких кадров).

## Ошибки и состояния

`State`: `INIT`, `CONNECTING`, `STREAMING`, `DEGRADED`, `STOPPED`. 
Статус `STREAMING` устанавливается после получения ключевого кадра. При сбое фонового режима запускается повторная сессия после `reconnect_delay_sec`, в режиме `on_demand` ошибка передаётся вызывающему коду, а обработка завершается. Для VAAPI предусмотрен пропуск отдельных повреждённых поверхностей: после 25 последовательных ошибок задействуется путь восстановления сессии без пересоздания ffmpeg контекста, codec контекста и тп.

Для подробностей API: [reader-api.md](reader-api.md). Статус: [support-status.md](support-status.md).
